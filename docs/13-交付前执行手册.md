# GovernForge 交付前执行手册

更新日期：2026-07-21

这份手册把最终验收拆成两类：Codex 可以在仓库内完成的工作，以及必须由项目 Owner 在真实 GitHub、模型供应商、身份系统和 Kubernetes 环境完成的工作。任何一项没有真实环境证据，都不能把状态改成“已验证”。

## 一、责任边界

### Codex 负责

- 修改后端、前端、Worker、CI/CD、Kubernetes 清单和文档。
- 补充单元测试、集成测试、浏览器测试、异常测试和安全门禁。
- 运行本地测试、构建、`pip-audit`、Compose/Kustomize 校验。
- 提交分支、创建 PR、修复 CI、更新验收证据和发布模板。
- 检查 GitHub App 接口实现、Webhook 幂等、Check 回写、受控 Auto-merge 的代码逻辑。

### 你负责

- 提供真实外部权限：GitHub App、模型供应商、OIDC、密钥系统、Kubernetes staging。
- 不把私钥、Webhook Secret、模型 Key 发到聊天或提交到 Git；只配置到 Secrets/Environment/密钥系统。
- 在 GitHub PR 中完成 CODEOWNER 审批；分支保护禁止 Codex 自行绕过。
- 在你的 Codex 和 Claude Code 本机安装 Hook，并各执行真实任务。
- 选择模型供应商、填写真实价格、确认预算和账单对账口径。
- 指定真实的 Security、SRE、FinOps、Engineering Owner，并完成发布签字。

## 二、你需要准备的外部材料

| 材料 | 用途 | 配置位置 | 不要做什么 |
|---|---|---|---|
| GitHub App ID、Slug、Private Key、Webhook Secret | PR/CI 入站和 Check 回写 | 本地 `.env` 或 GitHub Environment Secret | 不提交 `.env`、`.pem` |
| 两个 OpenAI-compatible 模型 Key | 主备路由和成本对账 | `MODEL_PROVIDER_*_API_KEY` 或密钥系统 | 不把 Key 写入模型路由数据库 |
| OIDC Issuer/Client/Secret | 企业登录和职责分离 | GitHub Environment/外部 Secret | 不继续依赖生产本地密码登录 |
| Kubernetes staging kubeconfig | staging CD、回滚、smoke | GitHub Environment 的 `KUBE_CONFIG_B64` | 不在聊天粘贴 kubeconfig |
| 一名 CODEOWNER 审核人 | PR 审批和职责分离 | `.github/CODEOWNERS` / GitHub 账号 | 不使用同一账号自审批 |
| FinOps 价格表和账单 | TCO、ROI、误差阈值 | 模型路由价格与验收表 | 不用估算值冒充真实账单 |

## 三、按顺序执行

### 1. 获取最新代码并确认治理基线

```powershell
cd D:\PyCharm\PyProjects\ai-app
git switch main
git pull --ff-only origin main
powershell -ExecutionPolicy Bypass -File .\scripts\verify-github-governance.ps1
```

预期：脚本输出 `Governance baseline verified: 8/8`。若失败，先修复 GitHub 可见性、分支保护或 required checks，不进入后续验收。

### 2. 启动本地环境

```powershell
cd D:\PyCharm\PyProjects\ai-app
Copy-Item .env.example .env -ErrorAction SilentlyContinue
docker compose up -d --build
docker compose ps
```

浏览器打开 `http://localhost:3000`。本地账号只用于开发验证，不能作为生产身份验收证据。

### 3. 安装并验证 Codex Hook

在目标代码仓库执行：

```powershell
$env:GOVERNFORGE_URL="http://localhost:8000"
$env:GOVERNFORGE_AGENT_TOKEN="<从连接器页面一次性签发>"
$env:GOVERNFORGE_WORKSPACE="ai_platform"
$env:GOVERNFORGE_ACTOR="你的企业邮箱"
governforge-agent-hook install --provider codex --root .
```

验证普通文件读取应 `allow`；修改 `auth`、迁移或部署文件应进入审批；后端断开时写操作应 `deny`，恢复网络后重复事件只能得到 `duplicate`。保存 Run ID、Action ID、Approval ID、Trace ID 和最终决策。

### 4. 安装并验证 Claude Code Hook

```powershell
governforge-agent-hook install --provider claude-code --root .
```

重复低风险、高风险、断网恢复三组用例。Codex 与 Claude Code 必须各有独立 Trace，不能用同一组模拟数据代替。

### 5. 配置真实模型网关

在“连接器 → 模型网关与成本”配置同一模型别名的两个路由，例如 `coding-default` 的 priority 10/20 主备路由。将 Key 配置到运行环境后执行：

```powershell
docker compose up -d --force-recreate backend worker
```

验证正常调用、主路由 429/5xx、主路由超时、预算超限和 Key 轮换，记录 provider、route、degraded、tokens、cost、Trace 与供应商账单金额。

### 6. 创建真实 PR 并验证治理链路

```powershell
cd D:\PyCharm\PyProjects\ai-app
git switch -c feature/governforge-acceptance-<你的名字>
Set-Content acceptance.txt "governforge acceptance"
git add acceptance.txt
git commit -m "test: governforge acceptance flow"
git push -u origin HEAD
```

在 GitHub 创建 PR，验证普通变更 allow、敏感变更 review/block、旧 SHA 不覆盖新 SHA、CI 失败不合并、补齐证据后自动更新 Check。保存 PR URL、Check URL、审计 Trace 和 API 响应。

### 7. 验证受控 Auto-merge

先验证待审批、CI 失败、SHA 变化、GitHub 冲突四个反例均不合并，再验证同 SHA、策略 allow、无待审批、required checks 全绿的正例才允许合并。所有结果保留 PR、Check、审计和 GitHub merge response。

### 8. 配置 staging CD

由你在 GitHub `Settings → Environments → staging` 配置 `KUBE_CONFIG_B64`，手动运行 Deploy workflow，选择 `staging` 和不可变 commit SHA。记录镜像 digest、migration Job、三个 workload rollout、smoke/health 响应及故障回滚前后版本。生产环境必须另设 `production` Environment 审批，不能复用 staging Secret。

### 9. 完成安全、备份和成本签字

由对应 Owner 完成 Secret/依赖/镜像扫描、OIDC/SCIM 撤销、数据库备份恢复、RPO/RTO、模型账单对账、审批人工成本和错误成本样本，并把报告链接、执行人、时间、commit/digest 写入 [最终交付与验收](./03-最终交付与验收.md) 的发布签字区。

## 四、交付判定

Codex 完成代码、测试、CI/CD、文档和审查；你完成真实 Agent、模型、GitHub PR、staging、身份和密钥验收，并组织 Product、Engineering、Security、SRE、FinOps/Data Owner 签字。任一项未完成，最终状态必须保持 `NO-GO`，项目只能称为 Release Candidate。

## 五、CI、CD 与合并的区别

| 机制 | 作用 | 本项目触发条件 | 是否自动合并 PR |
|---|---|---|---|
| CI | 验证代码能否构建、测试、扫描和渲染部署清单 | PR 或任意 push | 否 |
| `publish-snapshot` | 构建并推送 GHCR 镜像快照 | 仅 `main` 的 push；PR/功能分支显示 `Skipped` 是预期行为 | 否 |
| CD | 把通过 CI 的不可变镜像部署到 staging/production | `main` CI 成功后，或手动 workflow_dispatch | 否 |
| GovernForge Auto-merge | 在策略 allow 后请求 GitHub 合并 | 仓库显式启用、同 SHA、无待审批、CI 全绿、Installation 可用 | 受控条件满足时才会请求 |
| GitHub branch protection | GitHub 最终安全边界 | 每次合并都生效 | 可拒绝任何不合规合并 |

因此，`publish-snapshot (pull_request) Skipped` 不是失败。本次 PR #11 的实际结果是：`backend`、`frontend`、`postgres-integration`、`browser-e2e`、`images`、`manifests` 全部成功；只有只允许 `main push` 的镜像发布 job 被跳过。当前 workflow 和仓库设置不会因为 CI 成功而自动合并 PR。

## 六、第一次真实合并 PR

PR #11 当前状态是 `open / mergeable_state=blocked / reviews=none`。原因不是 CI 失败，而是 `main` 要求至少 1 个 CODEOWNER 审批和最近一次 push 由其他审阅者确认。当前 CODEOWNERS 是 `@wyxang0133`，所以个人账号不能有效完成自己的 PR 审批；需要邀请第二个 GitHub 账号作为协作者，并把该账号加入 `.github/CODEOWNERS`，否则普通 Approve 可能仍不满足 Code Owner 门禁。临时降低审批门槛不作为生产验收证据。

真实操作顺序：

1. 打开 PR #11，确认所有 required checks 为绿色。
2. 使用第二个协作者账号打开 `Files changed`，检查代码后点击 `Review changes → Approve`。
3. 回到 `Conversation`，点击 `Merge pull request`，第一次建议选择 `Squash and merge`，再点击确认。
4. 合并后打开 Actions，确认 `push main` 的 CI 运行；此时 `publish-snapshot` 才会执行并推送 GHCR 镜像。
5. CI 成功后 Deploy workflow 才会进入 staging；如果没有 `staging` Environment 的 `KUBE_CONFIG_B64`，部署会按设计失败并提示缺少集群凭据。
6. 合并后再同步本地 main 分支。

```powershell
git switch main
git pull --ff-only origin main
git branch -d docs/external-release-gates
```

合并按钮、审批、CI、镜像发布和部署分别对应不同的控制点；完成合并不等于完成生产部署。
